# Issue와 Pull Request를 읽기 쉽게 쓰기

처음 읽는 사람이 어떤 문제가 있었고 무엇이 달라지는지 이해할 수 있게 쓴다. 이 지침은 문서 표현과 커밋 설명을 위한 기준이다. 권한과 필수 검사는 [기여 기준](../../CONTRIBUTING.md), 에이전트의 파일 배정과 작업 기록은 [workflow](workflow.md)를 따른다.

## 제목과 본문

제목은 구체적인 대상과 동작을 담는다. `문서를 개선한다`보다 `작업 복원 결과와 검증 근거를 기록한다`처럼 달라지는 내용을 드러낸다. Issue는 해결할 문제를, PR은 최종 변경 결과를 중심으로 쓴다.

본문은 문제나 결과를 먼저 말하고 그 이유와 근거를 이어 쓴다. Issue에는 문제가 발생하는 상황과 기대하는 결과, 범위와 완료 조건을 적는다. PR에는 실제로 바뀐 동작이나 문서, 변경 이유, 검증 결과와 남은 한계를 적는다. 작업 범위가 바뀌면 제목과 본문도 최종 변경에 맞게 고친다. 대화 이력이나 중간 계획을 그대로 붙이지 않는다.

익숙한 한국어 문장을 기본으로 한다. 비교하거나 순서를 보여줄 때는 짧은 Markdown 목록을 쓴다. 제목과 본문에서 가운뎃점으로 명사를 나열하지 않는다. 화살표나 장식용 이모지로 문장을 대신하지 않는다. 일반 Markdown 제목, 목록, 체크박스와 코드 표기는 필요한 곳에 사용한다.

코드 경로와 프로토콜 이름은 정확하게 유지한다. 낯선 약어나 내부 용어는 처음 나올 때 의미를 설명한다. 예를 들어 CAS는 저장할 revision이 예상한 값과 같을 때만 갱신하는 검사라고 설명한다. 내부 agent 상태 문자열을 나열하는 대신 무엇이 끝났고 무엇이 남았는지 문장으로 쓴다. 기계가 읽는 필드와 상태값은 해당 계약의 형식을 유지한다.

## 근거와 한계

검사는 이름, 대상과 실행 결과를 함께 쓴다. 실패나 미실행을 숨기지 않는다. 실행하지 않은 검사는 구체적인 이유를 적고 통과했다고 쓰지 않는다. 이전 commit이나 다른 환경의 결과를 현재 변경의 통과 근거로 옮기지 않는다. 필요한 경우 명령, 대상 commit 또는 파일 hash와 로그 위치를 연결한다.

구현 담당자와 리뷰어, 승인 여부는 실제로 확인된 정보만 쓴다. 검토 요청과 승인 완료를 구분한다. 글을 작성한다는 이유로 사람을 자동 배정하거나 알림을 보내지 않는다. 비밀정보나 환자 원문은 설명과 로그에도 포함하지 않는다. 필요한 보안 검사나 승인 조건은 간결하게 쓰더라도 생략하지 않는다.

## 커밋 설명

검증과 필요한 검토가 끝난 변경 단위를 작업 중 커밋한다. 제목은 `docs: 작업 복원 결과를 기록한다`처럼 구체적으로 쓴다. 본문은 변경 내용, 이유와 검사 결과를 남긴다. 아래는 형식 예시이며 실제 검사 실행이나 통과 기록이 아니다.

```text
docs: 작업 복원 결과를 기록한다

새 작업에서 맥락을 복원한 결과와 사용량을 보고서에 남긴다.
후속 작업자가 검증 범위와 남은 한계를 확인할 수 있도록 근거를 연결한다.

검증: 실행한 검사 이름과 결과를 이곳에 기록한다.
실행하지 않은 검사와 이유를 이곳에 기록한다.
```

로컬 커밋과 원격 push, merge, 배포는 각각 실제로 허용된 범위에서 수행한다. 커밋에 포함할 파일을 고르고 생성된 SHA를 확인하는 절차는 [workflow](workflow.md)에 있다.
